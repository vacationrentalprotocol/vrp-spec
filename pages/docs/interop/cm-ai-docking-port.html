CM AI Docking Port and VRP: a field-by-field mapping

Status: Informative interop note. It changes nothing in VRP: no requirement, no field, no verification rule. It maps one independent protocol's question and answer onto VRP's, so that an agent can ask a CM Free node and a VRP node the same question and read the same kind of answer. The protocol's own text decides what it means; where this note and that text differ, that text wins. Date: 2026-10-24 Maps: CM AI Docking Port, protocol version 0.1 (Viljem Dvojmoč, CM Free, AGPL-3.0, source) onto VRP StayIntent Discovery v0.1, Core VRP v0.1 §2–§5 and the Node Tool Binding v0.1 proposal. Read on: 2026-10-24, from the Docking Port's landing page and its manifest (/.well-known/cm-ai-docking-port.json, HTTP 200 on cmfree.duckdns.org and ai-cmfree.duckdns.org). The Docking Port's long-form spec is its author's internal development log and is not read here.

1. What the Docking Port is

In its own words: "a standardized entry point for AI agents into the CM Ecosystem" and "a thin discovery and routing layer that lets any AI agent, speaking plain HTTP and JSON, find out what a CM instance can answer and how to ask." Each CM installation is a node. An agent calls one endpoint, Reception, with a Request Envelope; the node answers from its own data, and only when its local result is not positive forwards the same request to a small set of nearby, trusted nodes (depth-limited, geography-gated, loop-safe) and returns one Response Envelope. "The one rule that matters most: an AI agent talks only to Reception." Everything is read-only: "nothing an agent does through Reception creates a booking, a block, or any other write." There is no central server and no registry of nodes.

Four of those properties are the ones VRP's discovery layer requires of any index: a node answers for itself, a response that is incomplete says so, no central index, no write. The mapping below is therefore mostly renaming. The places where it is not renaming are listed in §6, with what a CM node that is also a VRP node does about each.

5. The tool name

The Docking Port names two capabilities, availability (local) and accommodation-discovery (ecosystem). Neither returns a signed offer, so the Node Tool Binding does not name them, and a node may keep calling them what it likes (binding §1, out of scope: "any tool other than the one bound here").

The binding applies the moment a CM node exposes its signed verified stay offer as a tool on any surface (MCP, A2A, WebMCP):

Binding ruleFor a CM node
Name (§3)exactly get_verified_stay_offer, on every surface, no prefix or vendor string
Arguments (§4)check_in, check_out, guests; the same three the Docking Port's query already carries under from, to, guests
Result (§5)the node's signed envelope, unmodified, as vrp_offer.php returns it today; no verdict, no summary
Origin (§6)served from a node URL (Core §2): the node's canonical_domain or www. followed by it, no other name
Who may use the name (§7)only the node itself; a Reception that forwards another node's offer is an operator surface and MUST NOT advertise the name

6. Where the two differ, and what a CM node that is a VRP node does

6.1 Identity: node_id is a label, canonical_domain is the node

A VRP agent verifies a node by fetching that node's own documents from its own domain (Core §2–§3). A node_id such as CM-AI-DEMO-058 gives an agent nothing to fetch. For a Reception response to be usable as StayIntent pointers, each results[] entry for a VRP node carries the node's domain and the three VRP pointers, read from that node's own discovery document and passed through unchanged:

{
  "node_id": "apartmamatevz.si",
  "canonical_domain": "apartmamatevz.si",
  "discovery": "https://apartmamatevz.si/.well-known/vacation-rental.json",
  "jwks_url": "https://apartmamatevz.si/.well-known/jwks.json",
  "verified_stay_offer_endpoint": "https://apartmamatevz.si/app/public/api/vrp_offer.php",
  "depth": 1,
  "source": "cm_node",
  "freshness": { "generated_at": "2026-10-24T09:00:00Z" },
  "data": { "...": "the node's own availability output, as today" }
}

The same three fields belong in service of the node's own Docking Port manifest, so that an agent that found the node through the Docking Port can step to VRP without guessing. The node's VRP discovery document is the source of these values; the manifest repeats them, it does not define them.

6.2 Availability data in the answer

A StayIntent response MUST NOT carry a price, a total or an availability total (§4.1): "price exists only inside the node's signed offer". results[].data is the node's availability output and stays the Docking Port's own. An agent reading a Reception response as StayIntent takes the pointers (§6.1) and ignores data; it then fetches the node's signed offer for check_in, check_out, guests, verifies the signature against the node's jwks_url, and reads price, availability and direct_booking_url from the verified offer and from nothing else (StayIntent §5, Core §5.1). Found is not bookable: a results[] entry means the node matched; a fresh, signature-valid offer with availability means it can be booked.

6.3 Forwarding is an index

When a Reception node forwards to neighbours and aggregates, it is, in VRP terms, running a StayIntent index over those neighbours. StayIntent allows that for anyone ("anyone may run a StayIntent index; multiple indexes coexist", §1, §2) on four conditions, all of which the Docking Port's own rules already meet or can meet without change:

  1. the response is pointers only; authority lives at each node (§2);
  2. no price, no availability total in the response (§4.1, see §6.2);
  3. no ranking, no score, no "best" (§4.2, §4.3);
  4. an incomplete answer does not pass as complete (partial, stricter than §2).

What an index may not become is a catalogue that holds the hosts: the Docking Port's "no central server", fallback-only forwarding and unmodified pass-through keep it on the right side of that line. This note does not decide anything beyond the mapping; a node's forwarding policy is the node's.

6.4 Geo

lat/lon maps to lat/lng. A label is a human trail, not a query term; where a named place is meant, StayIntent names it by Wikidata QID (near_wikidata) so that two nodes agree on what "Bled" is.

6.5 Two hosts today

On 2026-10-24 the Docking Port runs on a demo host (cmfree.duckdns.org, node CM-AI-DEMO-058, which its own text marks as carrying no real data), while the author's VRP node is apartmamatevz.si (discovery, JWKS and signed offers verified 2026-10-20; see IMPLEMENTATIONS.md). apartmamatevz.si serves no Docking Port manifest, and the demo host signs no offers. A Reception on the demo host that names apartmamatevz.si in a result is an operator surface for that node (binding §2, §7): the agent still verifies against apartmamatevz.si's own JWKS and goes to that domain's direct_booking_url. When the Docking Port runs on the VRP node's own domain, the two documents sit on the same domain and §6.1 is a matter of three fields.

7. Worked example

The question, as a Request Envelope to the demo Reception, and as the StayIntent query it is:

{
  "protocol": "CM-AI-Docking-Port",
  "version": "0.1",
  "request_id": "req-2026-10-24-example",
  "request_expiry": "2026-10-24T12:00:00Z",
  "origin": "ai-agent",
  "target": { "location": { "lat": 46.3683, "lon": 14.1146, "label": "Bled" }, "radius_km": 30 },
  "query": { "type": "availability", "from": "2027-07-03", "to": "2027-07-07", "guests": 4, "units": null },
  "limits": { "max_depth": 2, "max_distance_km": 40, "max_results": 10 },
  "visited": []
}
{
  "protocol": "vrp-stayintent",
  "protocol_version": "0.1",
  "geo": { "lat": 46.3683, "lng": 14.1146, "radius_km": 30 },
  "capabilities": [],
  "dates": { "check_in": "2027-07-03", "check_out": "2027-07-07" },
  "guests": 4
}

A results[] entry for the VRP node, carrying the §6.1 fields, read as a StayIntent pointer:

{
  "protocol": "vrp-stayintent",
  "protocol_version": "0.1",
  "match": "yes",
  "nodes": [
    {
      "canonical_domain": "apartmamatevz.si",
      "discovery": "https://apartmamatevz.si/.well-known/vacation-rental.json",
      "jwks_url": "https://apartmamatevz.si/.well-known/jwks.json",
      "verified_stay_offer_endpoint": "https://apartmamatevz.si/app/public/api/vrp_offer.php"
    }
  ],
  "note": "Not ranked. Deterministic match. Verify each node's signed offer (Ed25519) before quoting price or booking."
}

The agent's next step is VRP's, unchanged: fetch the node's verified stay offer for check_in=2027-07-03, check_out=2027-07-07, guests=4; verify the signature against the JWKS named in the node's own discovery document; quote only a fresh, safe-to-quote offer; send the guest to the direct_booking_url inside it, on apartmamatevz.si.

8. What this note does not do

  • It does not add a field, a requirement or a rule to VRP.
  • It does not make the Docking Port conformant to StayIntent. Conformance is shown against the vectors in this repository (StayIntent §8), by whoever runs them, with no approval from anyone (GOVERNANCE §6).
  • It does not rank, compare or recommend either protocol or any node.
  • It is not the Docking Port's specification. Its author's text is.
