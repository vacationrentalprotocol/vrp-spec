ADR 0013: VRP 1.0 — Core and Well-Known URI, with the evidence per rule

Status: Proposed Date: 2026-11-01 (first draft, pull request #178, withdrawn) · 2026-11-05 (rewritten) · 2026-11-13 (files, version decision, review rules and order of introduction brought into line; the evidence stated per requirement, as measured)

Related: spec/v1.0.md (the candidate text), spec/v0.1.md, spec/well-known-uri-v0.1.md, docs/implementation-report-1.0.md, GOVERNANCE.md §4–§6, ADR 0002, ADR 0005, ADR 0006, ADR 0009, ADR 0012, ADRs 0014, 0015 and 0016 (independent approval, review period, shared custody; pull request #182, not on main when this was written; this record is not marked ready for review before they are, and the links become local then), ADR 0017.

This record is substantive (GOVERNANCE.md §4): it changes normative requirements, schemas and vectors. It is in force only after the review period that applies when it is marked ready (28 days under ADR 0015 once that record is in force, and in any case not less than 28 days by the maintainers' choice), approval from two maintainers that counts on its current head as ADR 0014 D3 sets out, one of them independent (ADR 0014 D1), and merge. When the period starts again is set by ADR 0015 D2–D3. Merging it decides 1.0; it does not make 1.0 live (D9).

Context

GOVERNANCE §5 sets one condition for 1.0: at least one independent implementation beyond the reference node. On 2026-11-05 there are three signing nodes from two products, one of them independent (apartmamatevz.si, CM PRO, key_custody: self), and two verifier organizations, one of them independent of the reference implementer (vrp-independent-verifier). The first draft of this record (#178) declared the whole current text to be 1.0, changed protocol_version with a 30-day cut-off, accepted ADRs with zero or one implementation, and offered a conformance report (one run of one verifier) as evidence. It was withdrawn after review against the practice of the standards bodies VRP measures itself against: W3C Process §6.3.2 (independent implementations of each feature, by others than the authors) and §6.3.7 (a review of at least 28 days, features without implementations marked *at risk*), and RFC 6410 §2.2.

The implementation report holds one row per MUST of Core v0.1, measured on 2026-11-05 and re-read on 2026-11-08, 2026-11-09 and 2026-11-13, and a separate entry for every requirement that 1.0 adds or changes. For the v0.1 rules it shows: on the node side, two products cover every rule except key rotation (never exercised live) and the refund schedule (one product); on the verifier side, the independent verifier covers the signature, the key, the payload match and valid_until, and every other verifier rule is implemented by one organization.

Two more facts shape this record. Core §2 says protocol_version: MUST be 0.1 and six of the nine schemas on main pin it with const, so the version string is a normative requirement, not a label; and RFC 9864 (October 2025) marks EdDSA, the only alg name VRP accepts, as Deprecated in the IANA JOSE registry (ADR 0017).

Decision

D1. Scope. VRP 1.0 is spec/v1.0.md, Core, together with spec/well-known-uri-v0.1.md. Its rules are the rules of Core v0.1, which the implementation report shows with two independent products on the node side except the two parts at risk (D5), and the requirements this record adds or changes (D2, D3, D4), whose evidence is stated separately (D6). Every other document in spec/ (receipt v1, the transparency log, portable attestations, the status bitstring, structure declarations, StayIntent discovery, node seal, proof chain, domain continuity, node tool binding) stays a 0.x draft outside 1.0, each with its own path to a stable version when it has two independent implementations.

D2. The version string. protocol_version is "1.0" or "0.1". The two values name the same wire format, exactly as Ed25519 and EdDSA name the same operation (ADR 0017). A 1.0 verifier MUST accept either, with no end date. A node MAY declare either; nothing forces a node to change. The discovery document declares a version (§2, §7) and the signed offer declares its own (§5). They are two declarations: a verifier checks each, reads the offer's from the signed payload only, and accepts every pair of the two known values. A declared value is compared as written. An absent value, or any other value of any type, leaves the document or the offer unknown (§9) and the offer is never quoted. The four Core schemas exist in a 1.0 edition (discovery, jwks, verified-stay-offer, verified-stay-offer-verification-result, each *-v1.0.schema.json). An edition differs from its v0.1 edition in the value sets of protocol_version (enum) and alg (enum), and in its $id, its title and the descriptions that name the text; in nothing else, which npm test checks. The v0.1 text, schemas and file names stay published unchanged: they are identifiers, not versions, like /contexts/v1.

D3. Node page identification. Core §2.1 (a) and (b), the <link rel="protocol"> in the head and the visible rel="protocol" link whose text contains «VRP», become MUST in 1.0, as ADR 0006 recorded for the next MAJOR version. (c), (d) and (e) stay SHOULD. Every known node met (a) and (b) when this record was written (report, «Node measurements»).

D4. Algorithm names. ADR 0017 ships with 1.0: alg is Ed25519 or EdDSA in §3 and §5 of spec/v1.0.md, in the three 1.0 schemas that carry alg and in the vectors. spec/v0.1.md and the v0.1 schemas keep EdDSA only. The maintainers read GOVERNANCE §5 («the rules a verifier uses to accept an offer … do not change except through a MAJOR version») as covering the name alias, so the change rides the MAJOR version rather than a MINOR one; ADR 0017 D7 provided for exactly this reading.

D5. At risk. Two parts of Core are marked *at risk* in the candidate text, as W3C Process §6.3.7 allows: §3.1 rotation (two products carry the code, no node has rotated live) and §5.3 rules.refund_schedule (one product). These two, and no others, are at risk; the candidate text, this record and the implementation report use the words for nothing else. At risk means that the maintainers may remove the part before acceptance. It does not mean «evidence is missing»: a requirement whose evidence is outstanding stays in 1.0 and is listed as such (D6). A part marked at risk MAY be removed before acceptance without restarting the review period (ADR 0015 D3); the removal changes the content, so approvals are given again on the head that has it removed (ADR 0014 D3). A part removed moves to a 0.x document and can return in a MINOR version. ADR 0008 (key lifecycle K1–K6, zero nodes) is not part of 1.0.

D6. Evidence. The evidence for every rule is the implementation report: one row per MUST of Core v0.1, and one entry per requirement that 1.0 adds or changes. Each names the implementation, its organization, the exact commit or the UTC instant of a live measurement, and the result of a run. Evidence is code at a commit together with a run, or a live measurement; an intention is not evidence. Several products of one organization count once. The report lives outside this record so that a corrected measurement never restarts this record's review (ADR 0015 D2). Before this record is marked ready for review, the report is on main.

Where evidence is missing the report says *evidence outstanding*. On 2026-11-13 that is the case for the requirements this record adds, on the verifier side:

  • A verifier accepts Ed25519 in the JWS header and on the key (§3, §5). Implemented by this repository's own verifier and verify page only. The three shipped verifiers refuse it (hemmabo-mcp-server 7.1.0, @vacationrentalprotocol/vrp-verify 0.3.0, vrp-independent-verifier).
  • A verifier accepts a discovery document that declares "1.0" (§2, §7). Implemented by this repository's own verifier and verify page only. hemmabo-mcp-server 7.1.0 refuses every value but "0.1"; the other two do not read the discovery document.
  • A verifier refuses an offer whose signed payload declares an unknown version, or none (§5, §9). Implemented by this repository's own verifier and verify page only. None of the three shipped verifiers reads the offer's version: each accepts "0.2" as it accepts "1.0", so none of them shows support for "1.0" either.

On the node side nothing is outstanding: every node declares "0.1" and signs EdDSA, both of which 1.0 keeps valid, and every node meets §2.1 (a) and (b). No node declares "1.0" or signs Ed25519; both are MAY, and D9 puts nodes after verifiers.

This record does not claim two independent implementations for any requirement in that list. Before it is accepted, the report shows for each of them an implementation at a named commit with a recorded run over the vectors of D7, from the verifier the organization publishes and from the reference verifier; those two are one organization and count once. Whether acceptance also waits for a second organization is for the review to decide and is not assumed here. The production releases come after the decision (D9).

D7. Vectors and checks. They land with this record (GOVERNANCE §4, conformance-gated), and npm test runs all of them:

  • Ten signed-offer vectors, examples/conformance/offer/06–15. The algorithm name: seven vectors (ADR 0017 D4). The offer's version: 08-protocol-version-1-0-valid-fresh (an otherwise valid offer declaring "1.0" verifies), 09-protocol-version-unknown ("0.2" is unknown, unsupported_version, never quoted) and 15-protocol-version-missing (no version in the signed payload is missing_protocol_version, whatever the unsigned envelope says). Vectors 01–05, the v0.1 corpus, are byte-identical and still verify; the suite fails if any of the four combinations of version string and algorithm name loses its accepting vector.
  • The discovery document's version, apart from the offer's: examples/conformance/discovery-version/vectors.v1.0.json, fifteen discovery documents ("1.0" and "0.1" accepted; other strings, numbers, null, a list, an absent member and the pre-0.1 member version refused) and eight pairs of a discovery document and a signed offer whose versions are declared separately.
  • The four 1.0 schemas are read by scripts/validate-artifacts.mjs: what each accepts and refuses for protocol_version and alg, that every v0.1 example and vector still validates (v0.1 compatibility), that the v0.1 editions still refuse the new values, and that the two editions differ in nothing else (D2).

The repository's own verifier (scripts/conformance.mjs) and the site's verify page accept both names and both versions in the same pull request, so the vectors pass where they are published. A run of that verifier over the fifteen offer vectors is published as a conformance report beside the v0.1 report, which is kept as it is (it binds to the five-vector corpus at its own commit).

D8. Records. With this record, ADRs 0005, 0006, 0009, 0012 and 0017 become Accepted, because each is normative in the 1.0 text. Their evidence is what the implementation report shows and no more. ADR 0006 (§2.1 (a) and (b)): three nodes from two products, measured. ADRs 0009 and 0012: two products on the node side; on the verifier side one organization for the rules the independent verifier does not implement. ADR 0017: no shipped implementation yet (ADR 0017 D8; D6 above). ADR 0005 is a rule about the standard's own text and names no implementation. ADRs 0007 (receipt envelope) and 0008 (key lifecycle) stay Proposed: their implementations are one and zero. ADR 0004 is unchanged. §13 of the Core text is marked informative; the names in it stay.

D9. The chain, verifiers before nodes. In this order, each step measured in production before the next starts:

  1. This record, the candidate text, the 1.0 schemas and the vectors merge.
  2. @vacationrentalprotocol/vrp-verify and the reference verifier accept both version strings and both algorithm names, and refuse an unknown or absent version in the discovery document and in the signed offer (their own MINOR releases). Each release is measured by a run over the vectors of D7. Their code at a named commit, with that run, is the evidence D6 asks for before this record is accepted; the releases themselves come after it.
  3. Nodes MAY declare "1.0" and sign Ed25519; the reference nodes first, measured before and after; the independent node at its operator's pace, or never.
  4. A release of this repository tags 1.0, and the IETF draft is revised from the 1.0 text as -01 (the -00 submission is the editor's hand step and precedes it).

1.0 is live when step 4 is done and measured. Until then, every surface says «candidate».

Out of scope. Whether a security correction may be made inside 1.x without a new MAJOR version is a GOVERNANCE §5 question for its own amendment (§12), not decided here. A Core §2.1 checker is not a verifier rule.

Consequences

  • No node breaks: "0.1" and EdDSA stay valid for every verifier that follows 1.0, with no end date.
  • A cold reader of a discovery document can see "1.0" once a node declares it; «0.1» no longer reads as «draft» by default.
  • The verifier side is honest about its gap: rules with one organization are listed in the report, and the independent verifier's additions (§2, §5.1, §6 generated_at, §7, §9) are the shortest path to two. The requirements 1.0 adds have no shipped implementation when this is written; D6 lists them.
  • This is a substantive change: 28 days of review, two approvals that count on the current head, one independent, then the editor merges (GOVERNANCE §4; ADRs 0014–0015).
  • Nothing in 1.0 makes any implementation, the reference implementation included, necessary for verification (ADR 0002; GOVERNANCE §1).
