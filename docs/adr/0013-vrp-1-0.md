## Context

GOVERNANCE §5 sets one condition for 1.0: "VRP reaches 1.0 only after at least
one independent implementation exists beyond the reference node — a second
signing node proves VRP is a standard and not a single project's file format."
On 2026-11-01 the standard stands as follows:

- **Its own namespace.** The standard lives in its own GitHub organization,
  apart from the reference implementer (ADR 0003, accepted 2026-08-17).
- **An independent signing node.** apartmamatevz.si signs its own offers with
  its own key on its own domain (`key_custody: self`). Its operator is a
  maintainer with no affiliation to the reference implementer
  ([IMPLEMENTATIONS.md](../../IMPLEMENTATIONS.md),
  [MAINTAINERS.md](../../MAINTAINERS.md)). The one deviation from Core §5 found
  on it, an offer signed for a check-in date that had passed, was fixed and
  measured in production on 2026-11-01
  ([#172](https://github.com/vacationrentalprotocol/vrp-spec/issues/172)): at
  08:56:35 UTC that request was answered `400 checkin_in_past`, and at
  08:56:29 UTC an offer for a future stay verified against the node's own JWKS.
- **A settled wire format.** ADR 0012 (#150, merged 2026-10-29) fixed the stay
  asked for, real dates, the echoed fields and the offer lifetime.
  `price.minor_unit` (#164, merged 2026-10-30) fixed the unit of every amount.
  No pull request that changes the signed offer is open.

`protocol_version` is `"0.1"` in every offer and discovery document, and the
schemas pin it (`"const": "0.1"`). Semantic versioning reserves major version
zero for initial development, and GOVERNANCE §5 lets a security correction be
made inside 0.x without a version change. That latitude ends at 1.0.

## Decision

**D1. Content.** VRP 1.0 is the specification as it reads when this record is
merged: `spec/v0.1.md` with the accepted ADRs, the schemas and the conformance
vectors. 1.0 adds no feature and removes none. Only the version identifier
changes; no normative requirement changes.

**D2. Version and migration.**

- `protocol_version` becomes `"1.0"`.
- The order is verifiers first, then nodes, then the published text. Verifiers
  accept `"1.0"` and `"0.1"` before any node signs `"1.0"`.
- A verifier keeps accepting `"0.1"` for 30 days after the 1.0 release. After
  that, an offer that declares `"0.1"` is unknown (§9) to a 1.0 verifier and is
  not quoteable.
- Within 1.x, a verifier for any 1.x version reads every 1.x offer: a minor
  version only adds. A breaking change is a MAJOR version (GOVERNANCE §5) and
  runs in parallel with the version it replaces for years, not 30 days.

**D3. Evidence.** The independent implementation that meets GOVERNANCE §5 is
apartmamatevz.si, on the evidence above. Before the 1.0 release, each node
listed in IMPLEMENTATIONS.md is measured against the 1.0 rules and the result
is recorded as a conformance report v0.1
([docs/conformance-report.md](../conformance-report.md)); a report about a node
is published with its operator's agreement.

**D4. Records.** ADRs 0005, 0006, 0007, 0008, 0009 and 0012 become Accepted
with this record. Each has been normative on main since it was merged;
acceptance makes it part of 1.0. ADR 0004 concerns funding, not the protocol,
and is not changed here.

**D5. Vectors.** Two conformance vectors land with the version change, before
any verifier accepts `"1.0"` (GOVERNANCE §4, conformance-gated): an otherwise
valid offer that declares `"1.0"` verifies, and one that declares `"0.2"`, a
version that does not exist, is unknown and not quoteable.

**D6. The chain.** The change ships in this order, and each step is measured
in production before the next one starts:

1. `@vacationrentalprotocol/vrp-verify` accepts `"1.0"` and `"0.1"`.
2. The reference verifier (hemmabo-mcp-server) does the same.
3. The reference nodes sign `"1.0"`. The independent node moves at its
   operator's pace within the 30 days of D2.
4. The specification text, the schemas and the vectors are published as 1.0,
   with the landing-page stamp.
5. A release of this repository tags 1.0.
6. The IETF draft is revised as `-01`.

Before step 1, every occurrence of `0.1` across the repositories is listed and
classified as a version identifier, a file or route name, or prose. None is
changed without that list.

**Out of scope.** Whether a security correction may be made inside 1.x without
a new major version is not decided here.

## Consequences

- Merging this record decides 1.0. It does not make 1.0 live: 1.0 is live when
  step 5 of D6 is done and measured.
- After 1.0 the signed offer, the verification rules and the schemas change
  only through a MINOR version that adds, or a MAJOR version with a migration
  path (GOVERNANCE §5).
- Implementers change one thing: the version string they sign and accept,
  within the 30 days after the release.
- This is a substantive change (GOVERNANCE §4): at least seven days of review
  with no maintainer objecting, and approval from two maintainers.
