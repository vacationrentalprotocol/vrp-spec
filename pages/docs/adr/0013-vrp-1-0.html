ADR 0013: VRP 1.0 — Core and Well-Known URI, with the evidence per rule

Status: Proposed Date: 2026-11-01 (first draft, pull request #178, withdrawn) · 2026-11-05 (rewritten)

Related: spec/v1.0.md (the candidate text), spec/v0.1.md, spec/well-known-uri-v0.1.md, docs/implementation-report-1.0.md, GOVERNANCE.md §4–§6, ADR 0002, ADR 0005, ADR 0006, ADR 0009, ADR 0012, ADRs 0014, 0015 and 0016 (independent approval, review period, shared custody; pull request #182, merge not before 2026-11-11; the links become local when they are on main), ADR 0017.

This record is substantive (GOVERNANCE.md §4): it changes normative requirements, schemas and vectors. It is in force only after the review period that applies when it is marked ready (28 days under ADR 0015 once that record is in force, and in any case not less than 28 days by the maintainers' choice), approval from two maintainers on its current head, one of them independent (ADR 0014), and merge. Merging it decides 1.0; it does not make 1.0 live (D9).

Context

GOVERNANCE §5 sets one condition for 1.0: at least one independent implementation beyond the reference node. On 2026-11-05 there are three signing nodes from two products, one of them independent (apartmamatevz.si, CM PRO, key_custody: self), and two independent verifier organizations (the reference verifier and vrp-independent-verifier). The first draft of this record (#178) declared the whole current text to be 1.0, changed protocol_version with a 30-day cut-off, accepted ADRs with zero or one implementation, and offered a conformance report (one run of one verifier) as evidence. It was withdrawn after review against the practice of the standards bodies VRP measures itself against: W3C Process §6.3.2 (independent implementations of each feature, by others than the authors) and §6.3.7 (a review of at least 28 days, features without implementations marked *at risk*), and RFC 6410 §2.2.

The implementation report now holds one row per MUST, measured on 2026-11-05. It shows: on the node side, two products cover every rule except key rotation (never exercised live) and the refund schedule (one product); on the verifier side, the independent verifier covers the signature, the key, the payload match and valid_until, and every other verifier rule has one independent organization.

Two more facts shape this record. Core §2 says protocol_version: MUST be 0.1 and nine schemas pin it with const, so the version string is a normative requirement, not a label; and RFC 9864 (October 2025) marks EdDSA, the only alg name VRP accepts, as Deprecated in the IANA JOSE registry (ADR 0017).

Decision

D1. Scope. VRP 1.0 is spec/v1.0.md, Core, together with spec/well-known-uri-v0.1.md. It includes every rule the implementation report shows with two independent products on the node side. Every other document in spec/ (receipt v1, the transparency log, portable attestations, the status bitstring, structure declarations, StayIntent discovery, node seal, proof chain, domain continuity, node tool binding) stays a 0.x draft outside 1.0, each with its own path to a stable version when it has two independent implementations.

D2. The version string. protocol_version is "1.0" or "0.1". The two values name the same wire format, exactly as Ed25519 and EdDSA name the same operation (ADR 0017). A 1.0 verifier MUST accept either, with no end date. A node MAY declare either; nothing forces a node to change. The four Core schemas exist in a 1.0 edition (discovery, jwks, verified-stay-offer, verified-stay-offer-verification-result, each *-v1.0.schema.json) that differs from the v0.1 edition in protocol_version (enum) and alg (enum) only. The v0.1 text, schemas and file names stay published unchanged: they are identifiers, not versions, like /contexts/v1.

D3. Node page identification. Core §2.1 (a) and (b), the <link rel="protocol"> in the head and the visible rel="protocol" link whose text contains «VRP», become MUST in 1.0, as ADR 0006 recorded for the next MAJOR version. (c), (d) and (e) stay SHOULD. Every known node met (a) and (b) when this record was written (report, «Node measurements»).

D4. Algorithm names. ADR 0017 ships with 1.0: alg is Ed25519 or EdDSA in §3 and §5, in the 1.0 schemas and in the vectors. The maintainers read GOVERNANCE §5 («the rules a verifier uses to accept an offer … do not change except through a MAJOR version») as covering the name alias, so the change rides the MAJOR version rather than a MINOR one; ADR 0017 D7 provided for exactly this reading.

D5. At risk. Two parts of Core are marked *at risk* in the candidate text, as W3C Process §6.3.7 allows: §3.1 rotation (two products carry the code, no node has rotated live) and §5.3 rules.refund_schedule (one product). A part marked at risk MAY be removed before acceptance without restarting the review (ADR 0015 D3). A part removed moves to a 0.x document and can return in a MINOR version. ADR 0008 (key lifecycle K1–K6, zero nodes) is not part of 1.0.

D6. Evidence. The evidence for every rule is the implementation report, one row per MUST with a live measurement (UTC) or a file and line at a commit, and not the conformance report v0.1 (one run of one verifier). The report lives outside this record so that a corrected measurement never restarts this record's review (ADR 0015 D2). Before this record is marked ready for review, the report is on main.

D7. Vectors. Four signed-offer vectors land with this record (GOVERNANCE §4, conformance-gated): 06-alg-ed25519-valid-fresh and 07-alg-unexpected (ADR 0017 D4, now as 1.0 offers), 08-protocol-version-1-0-valid-fresh (an otherwise valid offer declaring "1.0" verifies) and 09-protocol-version-unknown (an offer declaring "0.2" is unknown, unsupported_version, never quoted). The repository's own verifier and the site's verify page accept both names and both versions in the same pull request, so the vectors pass where they are published.

D8. Records. With this record, ADRs 0005, 0006, 0009, 0012 and 0017 become Accepted: each is normative in the 1.0 text and has two independent products behind it. ADRs 0007 (receipt envelope) and 0008 (key lifecycle) stay Proposed: their implementations are one and zero. ADR 0004 is unchanged. §13 of the Core text is marked informative; the names in it stay.

D9. The chain, verifiers before nodes. In this order, each step measured in production before the next starts:

  1. This record, the candidate text, the 1.0 schemas and the vectors merge.
  2. @vacationrentalprotocol/vrp-verify and the reference verifier accept both version strings and both algorithm names (their own MINOR releases).
  3. Nodes MAY declare "1.0" and sign Ed25519; the reference nodes first, measured before and after; the independent node at its operator's pace, or never.
  4. A release of this repository tags 1.0, and the IETF draft is revised from the 1.0 text as -01 (the -00 submission is the editor's hand step and precedes it).

1.0 is live when step 4 is done and measured. Until then, every surface says «candidate».

Out of scope. Whether a security correction may be made inside 1.x without a new MAJOR version is a GOVERNANCE §5 question for its own amendment (§12), not decided here. A Core §2.1 checker is not a verifier rule.

Consequences

  • No node breaks: "0.1" and EdDSA stay valid for every verifier that follows 1.0, with no end date.
  • A cold reader of a discovery document can see "1.0" once a node declares it; «0.1» no longer reads as «draft» by default.
  • The verifier side is honest about its gap: rules with one independent organization are listed in the report, and the independent verifier's additions (§2, §5.1, §6 generated_at, §7, §9) are the shortest path to two.
  • This is a substantive change: 28 days of review, two approvals on the current head, one independent, then the editor merges (GOVERNANCE §4; ADRs 0014–0015).
  • Nothing in 1.0 makes any implementation, the reference implementation included, necessary for verification (ADR 0002; GOVERNANCE §1).
