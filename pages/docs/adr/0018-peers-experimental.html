ADR 0018: Peers, an Experimental Way for Nodes to Name Other Nodes

Status: Proposed Date: 2026-11-07 (proposed)

Related: spec/peers-v0.1.md, ADR 0002, GOVERNANCE.md §2, §4, §5, StayIntent Discovery v0.1.

Context

Core v0.1 says how an agent verifies a node whose domain it already knows, and forbids making that depend on a central list: "Verification MUST NOT require HemmaBo, a VRP-operated trusted issuer registry, a host accreditation program, a certification company, or a central discovery index" (spec/v0.1.md §1). It does not say how an agent that knows one node can find another. StayIntent Discovery v0.1 answers a stay request with pointers and lets anyone run an index ("No index is privileged", §2), but an index, too, has to learn which nodes exist.

So today every way from one node to the next is a list someone keeps. Whoever keeps the only list everyone starts from stands in the middle, whatever the specification says. GOVERNANCE.md §2 lists a "central discovery index" among the things VRP must not require as a precondition for verification.

Measured 2026-11-07, GET /.well-known/vacation-rental.json on the three VRP nodes known to the maintainers: villaakerlyckan.se (16:03:54 UTC, 44 top-level members), apartmamatevz.si (16:08:57 UTC, 8) and lakeviewhome.se (16:08:59 UTC, 42). None has a member named peers, and none names either of the other two. The two nodes in IMPLEMENTATIONS.md are two of the three.

Two rules already in force let a node add a member without touching Core. Well-Known URI v0.1 §3: "Clients MUST ignore unknown fields and MUST treat the document as advisory metadata only". The Core discovery schema (schemas/discovery-v0.1.schema.json) has no additionalProperties, so an extra member is valid against it.

Decision

D1. A separate, experimental document. spec/peers-v0.1.md, status Experimental, defines one optional member of the discovery document, peers, with its own schema schemas/peers-v0.1.schema.json. Core v0.1, the Well-Known URI document, the Core discovery schema and every rule a verifier uses to accept an offer stay as they are. Nothing in the document is part of Core conformance.

D2. Domains only. peers has three members: spec (the identifier of this version), nodes (zero to 100 domains) and an optional updated_at. An entry is a domain written as Core §2 writes canonical_domain, meets Core §2's host-owned domain rule, and is not the listing node's own domain. Nothing else about a node may appear: no name, URL, price, distance, score or category.

D3. No order. Entries appear once each, in ascending code-point order, and a client treats them as a set. An order anyone can recompute leaves no first place to sell or to read as a recommendation.

D4. No trust. An entry is not a trust relation, endorsement, partnership or rating, and is not reciprocal. A client reaches a listed domain by building https://{domain}/.well-known/vacation-rental.json itself and checking the document under Core §2 for that domain; until then the domain is not a node. Quoting anything still requires Core §3–§9. Absence from a list, and the number of lists a domain appears on, are no statement about the domain either: a client reads neither as a signal (§4 item 4, §6 item 7). Without that rule a client could rank nodes by how often they are named, and the lists would have rebuilt the middle they were written to remove.

D5. Bounded walks. A client that follows peers bounds depth, fetches and time (RECOMMENDED 3, 100, 10 seconds per fetch), fetches each domain once, follows only nodes it has reached, connects to no non-public address, honours Retry-After, never presents a walk stopped by a limit as complete, and never ranks the result.

D6. No seed, no registry. The document names no starting node or list, and no starting point is privileged. A node that lists no one, and that no one lists, is still a node.

D7. No signature on the list in v0.1. A list can only point at domains that must then prove themselves (D4). A signature would not change what a client may conclude, and would add key handling.

D8. Conformance. examples/conformance/peers/negative.v0.1.json (30 cases: members a client ignores in full and entries it skips, each with its name, and three valid controls) and positive.v0.1.json (a five-domain network, six walks, each run twice with the entries in reverse order to show the result does not depend on it), checked offline by scripts/verify-peers.mjs in npm test. scripts/validate-artifacts.mjs checks every member in the vectors against the peers schema and every document in the network against the unchanged Core discovery schema; its schema checker gains maxItems and uniqueItems.

D9. Leaving Experimental. The document becomes a public draft by a later ADR, when two independent implementations publish peers, a walk that starts at a node of one reaches a node of the other and back, with no code or data of either in the other's path, and at least one client written by neither publisher performs that walk and reports the same set from both starts. Two publishers alone show that the member can be written; a client of a third party shows that it can be read.

D10. At risk. Three parts of the text are marked at risk: ascending order as a requirement (§3.2), the cap of 100 (§3.3) and the recommended defaults for a walk (§6 item 1). A part marked at risk MAY be changed or removed in response to review without this record being withdrawn; any other change to the normative text is a new proposal under GOVERNANCE.md §4 (and restarts the period under ADR 0015 D2–D3, once accepted). Evidence gathered in review is recorded under "Open questions for review" below; the first such entry, on depth, is why the walk defaults are not compared with a relay's.

Alternatives considered

  • No peers; each software publishes its own seed list. Rejected as the only mechanism: every way from one node to the next stays a list someone keeps, and a client that starts from the most complete list has made its keeper the middle. Seed lists remain one of the ways a walk may start (§7).
  • URIs instead of domains. Rejected: Core §2 identifies a node by its registrable domain and fixes the discovery URL (RFC 8615), so a URI adds nothing but a way for a list to send a client somewhere else (§3.1, §5).
  • A signed list. Deferred (D7): the list proves nothing a signature would strengthen, and it would add key handling to every publisher.
  • A registry of nodes or of lists. Out of bounds: GOVERNANCE.md §4 and ADR 0002 forbid a central registry, and the W3C TAG's Web Platform Design Principles §11.3 reserve a registry for extensions that "a wider set of participants" define, which peers has none of.
  • Node discovery inside the StayIntent response. Rejected: matching a stay and knowing which nodes exist are different questions; an index needs the second before it can answer the first, and mixing them ties node discovery to one index's answers.
  • A relay or index without peers. Not an alternative but a later layer: an index still has to learn which nodes exist, and peers is one way it may.

Consequences

  • Version class. Additive. No Core requirement changes, no schema a Core verifier reads changes, and nothing a verifier accepts or rejects changes. A v0.1 client ignores peers (Well-Known URI §3). Known nodes affected: none (none publishes a member named peers, measured above).
  • Not part of 1.0. The document is outside Core and outside the Well-Known URI document, the two documents the proposed 1.0 record names as its scope (ADR 0013 D1, pull request #187, not accepted). Accepting this record neither waits for nor delays that one.
  • Substantive under GOVERNANCE.md §4: it adds normative text and a schema. This record, at least seven days of review with no maintainer objecting, and two approvals, as GOVERNANCE.md §4 requires since 2026-10-23 (MAINTAINERS.md). If ADR 0014 and ADR 0015 (pull request #182) are accepted first, one approval comes from a maintainer independent of the author, and the period for specification text, schemas and vectors is 28 days.
  • Neutrality (GOVERNANCE.md §2, ADR 0002): no list is required, no list is privileged, every listed node proves itself on its own domain, and the rules bind every publisher and client alike, the reference implementation included. The normative text names no implementation; the informative §12 points to this repository's interop note on an independent implementation, as docs/interop-and-trust-positioning.md already does.
  • Implementations follow in their own repositories, after acceptance. This repository holds the text, the schema and the vectors; a live walk across independent nodes is the evidence D9 asks for.

Open questions for review

  1. The default depth: 3 here; the CM AI Docking Port's limits_default uses max_depth 2 (interop note). At risk (D10). Answered in review (Viljem Dvojmoč, independent implementer, pull request #190, 2026-11-07 20:51 and 21:00 UTC): the two numbers bound different things and are not comparable. A peers walk is client-driven and sequential: the client fetches one discovery document at a time, every node answers only for itself, nobody forwards on anyone's behalf, and the cost lands on the client (§6). The Docking Port's Reception is server-driven forwarding: one request can make a node call max_fanout neighbours in parallel, each of which can do the same, so cost grows as fanout to the power of depth and lands on the operators who forward; that is why its design (decided 2026-09-29, in its own words: "the real question isn't 'how deep' but 'how many nodes does a node talk to in parallel on one hop'") caps depth hard and makes fanout the lever. A node that would never accept depth 3 on its own Reception is therefore safe as an entry in a depth-3 walk: the 3 means three sequential fetches by the client. peers defines no forwarding (§12), and the client-side counterparts of fanout are the fetch budget and the one-request-at-a-time rule (§6 items 1 and 5). The defaults stay as they are; the question is closed, the at-risk mark remains for implementation evidence on the numbers themselves.
  2. The cap of 100 entries per node. At risk (D10).
  3. Whether ascending order (D3) should stay a requirement or become a recommendation. At risk (D10).
  4. Whether updated_at earns its place, or HTTP caching suffices.
  5. Whether a later version signs the list (D7).
