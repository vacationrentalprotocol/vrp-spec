This report is data; it decides nothing.

Summary for the 1.0 record

  • Node side: every MUST has two independent products with ✔, except §3.1:165 (rotation never exercised; C not read) and §5.3:448 (one product publishes a schedule). Both at risk.
  • Verifier side: the reference verifier (V1) and the independent verifier (V5) together cover: §1, §3.1 kid, §5.1 reference id and unknown parameters, §5.1 stale, §6 valid_until, §8, Well-Known §3. Every other verifier rule has one independent organization only (V1), because V5 implements the signature, the key, the payload match and valid_until and nothing else. Those rules are at risk on the verifier side until a second organization implements them. The gap is one implementation away: V5 adding §2 (host-owned domain, fetched domain), §5.1 (booking URL), §6 (generated_at), §7 and §9.
  • Rules the shipped verifiers apply since 2026-11-08: §6:502 and the §5/§7 lifetime, date, language and request-match rules are enforced by V1 (7.0.13) and V2 (0.3.0) as well as by V3 and V4; until that date neither shipped verifier applied them (releases v7.0.13 and v0.3.0, 2026-11-08). The independence column on those rows is unchanged (no): V1 and V2 are one organization, and V5 does not apply them. V2's §7:512 is met for the library's part only; the discovery document and the transport stay with its caller. V1's §7:512 is partial: §7:514 and §7:516 pass when canonical_domain or protocol_version is absent from the discovery document (lib/vrp.ts:257–265 falls back to the pre-0.1 version field and to the fetched domain), found and reproduced by the independent reviewer on 2026-11-09; the correction is handled separately, with a regression test for each case. §5.3:432 (rounding) is computed by no one.
  • Not checked: CM PRO key rotation (§3.1:165); whether V5 is still maintained.
